## 一、结论摘要

**综合完成度约 63%**，其中：

- **工程实现完成度约 71%**：内核主干、VFS、网络、UI、AI、测试体系均已形成可运行闭环。
- **自动化验证完成度约 80%**：955 项 ctest 全部通过，CI 覆盖 6 个固件目标与多类质量门禁。
- **真机与产品化完成度约 30%**：所有自动化运行验证均为 host 或 QEMU，两个真实硬件目标仅到“可编译”级别。
- **文档一致度约 55%**：README 信息量大，但存在测试数量滞后、引用文档缺失、少数功能状态超前于代码。

**阶段判定：Alpha 后期 / Beta 前夜。**

一句话概括：**它已经是一套在 QEMU 上跑得通、测试覆盖相当完整的微内核操作系统工程原型；但还不是一套经过真机验证、默认启用用户态隔离、可以直接交付的产品级 OS。**

---

## 二、评估口径

完成度不是单一维度。本报告将“完成度”拆为四个维度，并给出不同权重：

| 维度 | 权重 | 判断依据 |
|------|:----:|----------|
| 代码实现 | 45% | 功能是否真实存在、是否有明确接口与错误处理、是否只是头文件/占位 |
| 自动化验证 | 25% | 是否有单元/集成测试、是否被 CI 执行、QEMU 启动断言是否覆盖 |
| 真机与产品化 | 20% | 是否在真实硬件上启动、驱动是否标定、安全配置是否可用于生产 |
| 文档与生态 | 10% | README/DOCS 是否与代码一致、SDK 是否可用、是否有可交付说明 |

综合得分按 `71×45% + 80×25% + 30×20% + 55×10% ≈ 63%` 计算。

子系统评分采用同一口径：90–100 为可交付稳定状态，75–89 为主干完整但存在明确边界缺口，60–74 为可运行原型、关键路径部分闭环，40–59 为骨架或局部实现，40 以下为实验/占位。

## 五、分项结论

### 5.1 内核核心：80%

已具备的真实实现：

- `kernel/task/task.hpp`：32 级优先级、TCB 组合式上下文（Task/Scheduler/Memory/Ipc/Security）、就绪位图与 O(1) 选路。
- `kernel/scheduler/frame_scheduler_v2.cpp`：动态 VSync 帧周期、EMA 平滑、tickless 等待与帧窗口任务拦截。
- 各架构启动/切换汇编真实存在：cm3/cm0plus/cm7 的 `boot.S`，cm4f/cm7 的 `context_switch.S`，RV32 的 `trap_vector.S`，AArch64 的 `exceptions.S`。
- `kernel/core/ipc.cpp`：Endpoint、阻塞/应答状态、优先级继承；`kernel/core/cspace.cpp`：16 槽位位图、cap_insert/lookup/revoke/级联清理。
- `kernel/mm/memory.cpp`、`kernel/mm/mmu.cpp`：TLSF 堆、全局 new/delete、AArch64 页表与任务地址空间。
- `kernel/core/syscall_dispatcher.cpp`、`syscall_validator.cpp`：SVC/ECALL 分发、用户指针校验、内核段隔离。
- `arch/riscv/rv32imac/arch_impl.hpp`：PMP 区域配置代码存在，说明 RISC-V 侧并非只有特权级切换。

主要缺口：

- host 测试用 `tests/stubs/arch_api.hpp` 替换了整套架构层，真正验证上下文切换的只有 QEMU 板上自检。
- 调度器、信号量、消息队列、TaskNotify 的独立测试不如 IPC/CSpace 充分；FrameSchedulerV2 的 VSync/EMA/tickless 路径缺少直接 host 测试。
- AArch64 目标仍标注实验性，2026-11-21 的 README 也将其列为 bootstrap 观察期。

### 5.2 架构与板级：68%

- 6 个目标均可通过 CMake 解析并编排出完整源集合；`boards/*/board.cmake` 对 CPU flags、链接脚本、板级源、编译宏做了明确分工。
- QEMU 4 目标有串口断言；lm3s/rv32/mps2 还编入了 `selftest`。
- Nucleo-L031K6（64KB Flash / 8KB RAM）与 MiBand 8（576KB Flash / 384KB SRAM）有真实板级代码，但仓库内没有真机启动日志、烧录脚本或 HIL 记录。
- 大小预算只覆盖 4 块板；rv32/aarch64 没有 `size_budget.json` 条目。

**结论：**“能在 QEMU 上跑”是成立且被反复验证的；“能在真机上跑”目前只有编译证据，没有运行证据。

### 5.3 VFS 与存储：82%

- `vfs/vfs.cpp` 提供 VNode 多态、RamFS、ProcFS、LittleFS 与 PhotonCache；`services/vfs/vfs_service.cpp` 对跨信任域调用做能力校验（fail-closed、内核旁路、Device 能力 rights 匹配、撤销即时生效）。
- 8KB RAM 的 M0+ 目标做了裁剪：RamFS、LittleFS、SoftBus 在该目标不编入。
- host 测试覆盖 VFS、RamFS、ProcFS、LittleFS 契约、PhotonCache、路径遍历与权限负向用例。

缺口：

- virtio-blk 只实现了块设备与 `disktest`，LittleFS 尚未挂载到 virtio-blk。
- SoftBus 在 M0+ 被裁掉；其余目标有实现，但没有多设备联调。
- 掉电安全只有日志式文件系统与重试逻辑的 host 测试，没有真实掉电 HIL。

### 5.4 网络与互联：68%

- lwIP 2.x、防火墙、包捕获、扫描器、分布式软总线、BLE HCI/NimBLE、StealthIdentity、BleStealth、BleIDS 均有实际 `.cpp/.hpp`。
- QEMU lm3s 的启动断言覆盖网络初始化与 ping 失败路径；rv32/aarch64 的 virtio-net 能通过 DHCP 获取地址，并有 `disktest`/`gputest` 自检。
- 网络分层（LinkLayer/ProtocolRegistry）在 host 测试中验证了解耦。

缺口：

- 扫描器与无线 Lua 绑定只在 lm3s 目标编入；rv32/aarch64/mps2 是“有 lwIP、无扫描器”的配置。
- virtio-net 未接入 PacketCapture/Firewall 过滤链。
- WiFi 的 RTL8187L/RTL8812AU 驱动缺物理 USB 硬件，无法验证。
- BLE 只在 miband 目标编入，且没有真机 HIL；NimBLE 桥接主要靠 host 测试证明。
- “分布式软总线”目前是单机/主机测试级能力，没有两设备以上联调记录。

### 5.5 安全防护：65%

已有实现：

- NIDS（`security/ids/`）、HIDS（`security/hids/`）、自动响应（`security/response/`）、AuditEngine、SecurityMonitor、WatchdogManager。
- 安全启动：Ed25519 验签、A/B 分区、OTA 解包；`bootloader.elf` 仅 lm3s 目标构建。
- 系统调用层有明确的用户指针校验、内核段保护、kill/dev_register 特权检查。
- 安全负向测试与 IDS/HIDS/响应测试均在 955 项中通过。

关键问题：

- **除 nucleo 外的 5 个板级 `board.cmake` 都定义了 `CONFIG_OTA_DEV_MODE=1`，包括 miband8。** 该模式使用 mock Ed25519 与占位公钥，任何签名都能通过验证。
- 4 个 QEMU 目标与 nucleo 定义了 `DEBUG_BYPASS_SOFTBUS_KEY`，绕过 SoftBus 每设备密钥的 fail-closed 校验；只有 miband 走真实 OTP 密钥路径。
- 安全启动只在 lm3s 有 bootloader 目标，miband 没有对应的生产启动链。
- NIDS 只在 lm3s 编入；HIDS/响应任务在 nucleo/miband 被裁掉。
- 没有任何渗透测试、红队验证或真实攻击面评估记录。

**结论：**安全机制“写出来了”，但“默认配置可安全交付”不成立。

### 5.6 UI 框架：78%

- `ScreenNavigator` 页面栈与 8 向转场、手势识别、`SwitchView/ScrollView/ImageView/DialogView/TextView` 等控件、UTF-8/4bpp 字体、条带模糊、`OverlayRootView` 浮层均有实现和 host 测试。
- 字体管线包含 `.afont` 流式按需读取、LRU 缓存、分带一致性与回退逻辑。
- 高斯模糊为 Q16 定点、可分离卷积、零堆分配，并有 18 项测试。

缺口：

- UI 真正实例化只在 miband8 的 watch app；lm3s 等 QEMU 目标主要跑 shell/网络/显示 mock。
- ST7789、GT316 触摸等真实硬件驱动没有真机标定；UI 的“可穿戴体验”尚未在真实屏幕/触控上验证。
- 动态表盘宿主（Lua/QuickJS）有代码与测试，但依赖脚本引擎在 miband 上的运行时表现，后者同样未真机验证。

### 5.7 应用、运行时与脚本引擎：60%

- `apps/kernel.cpp` 是 lm3s/rv32/mps2/aarch64 的启动链；`apps/m0plus_main.cpp` 是 M0+ 极简链；`apps/watch/miband_main.cpp` 是 MiBand 链。
- `apps/elf_loader.cpp` 用 `TaskPrivilege::User` 创建任务，带 W^X、地址回绕、MPU 沙盒校验；这是目前最明确的用户态路径。
- Lua 5.4.6 有独立 32KB `LuaHeap`；QuickJS 有独立 `JsHeap` 与指令预算/熔断器；两者都有 host 测试。

缺口：

- **内置应用绝大多数是内核特权任务。** `kernel.cpp`、`miband_kernel.hpp`、`m0plus_main.cpp` 中创建的 shell/daemon/ui/render 任务均使用默认 `TaskPrivilege::Kernel`；只有 ELF 加载的应用显式使用 User。
- `apps/sandbox_test_app.cpp` 没有被任何板级源列表编入，用户态沙盒的固件级回归依赖 ELF 路径。
- Lua 与 QuickJS 默认只在 miband8 启用；其他目标默认关闭。README 的“双脚本引擎”是能力描述，不是所有目标的默认运行配置。
- 没有应用包管理、签名安装、权限声明与实际分发链路；SDK 只保证模板可编译与契约同步。

### 5.8 服务化（services/）：45%

这是与 README “微服务架构”叙事差距最大的部分。

- `services/` 下有 vfs、net、firewall、sensor、power、display、notification、ble 八个服务目录，`service_manager`/`service_registry` 也存在。
- 真正编入固件的只有：`services/vfs/vfs_service.cpp`、`services/firewall/*`、`services/net/net_service.cpp`（仅 virt 板）、`services/notification/notification_center.cpp` 与 `services/ble/ble_stack.cpp`（仅 miband）。
- `services/sensor`、`services/power`、`services/display`、`services/service_manager.cpp` 主要出现在 host 测试源集合中，没有进入任何固件目标。
- 即使编入固件，服务也是内核线程或同地址空间对象，不是独立地址空间、独立能力域的进程。

**结论：**“服务化”目前是接口与代码组织层面的服务化，不是隔离层面的微服务化。

### 5.9 AI 运行时（February）：65%

- `ai/february/` 的 EventBus、IntentEngine、Planner、Persona、SoftBus、PeerTable、FirmwareBridge 均为真实代码，全部 header-only、零堆分配、固定容量。
- `FirmwareBridge` 在 `apps/kernel.cpp`、`apps/net_app.cpp`、`apps/watch/watch_app.cpp` 有实际调用点，lm3s 与 miband 均接入。
- 有端到端、可靠性、SoftBus 集成测试。

定位需要澄清：

- 它是**规则表 + 关键词匹配 + 冷却/锁存**的确定性意图引擎，不是大模型推理，也没有模型加载/量化/算子后端。
- “跨设备意图协同”只有 codec/transport/adapter 和 host 测试，没有两设备实机联调。
- legacy `ai/intent_engine.hpp` 仍在，存在两套意图实现并存的维护成本。

### 5.10 驱动层：60%

- 显示（帧缓冲、SSD1306、ST7789、OLED Mock）、输入（GT316、按键、手势）、传感器（心率、BHI260AP、健康算法）、RTC（DS3231）、RF 频谱、USB、存储、电源、virtio（blk/gpu/net）、camera、NFC 均有代码。
- 驱动普遍经 `hal/` 抽象，板级在 `boards/` 提供工厂，方向正确。
- host 测试覆盖大量驱动协议与寄存器逻辑。

缺口：

- BHI260AP 需要固件上传才能产出数据，该项未完成；passthrough 标定待真机。
- DS3231 未实现硬件闹钟，闹钟调度走 ProcessTimerManager；真机 HIL 未验证。
- ST7789、GT316、BLE UART 等真实硬件路径只有编译与 host 测试，没有真机波形/时序验证。
- camera、NFC、GUIX、WiFi 仍在 `experimental/` 或非固件路径；README 中部分 ✅ 标注超前于实际接线。

### 5.11 测试与 CI：88%

这是项目最扎实的部分之一。

- 955 项 ctest 实测全部通过，覆盖内核、VFS、网络、安全、UI、AI、驱动、实验模块。
- `build.yml` 覆盖 6 目标构建、QEMU 串口断言、Kconfig 矩阵、SDK 模板、固件大小预算、clang-format、cppcheck、clang-tidy、gitleaks、ASAN/UBSAN、TSAN、fuzz、CodeQL、架构依赖扫描。
- `driver_htl.yml` 另有 5 个驱动专项 job。
- 架构依赖扫描本轮实测退出码 0，依赖 16 条带理由的白名单例外。

仍需注意：

- 覆盖率 ratchet 的 `COVERAGE_MIN_LINE` 仍为 `0.0`，即“只报告不拦截”。
- `unit-tests-32bit` 为 `continue-on-error: true`，仍是观察期。
- 编译告警棘轮只有 4/6 板有基线；rv32/aarch64 为报告模式。
- 固件大小预算只有 4/6 板。
- `compliance-check` 在 `compliance_baseline.md` 缺失时打印 INFO 并跳过，实际不构成门禁。
- 没有真实硬件 HIL；所有“HIL”均为 QEMU 仿真。

### 5.12 文档：55%

- README 约 100KB，信息密度高，架构、命令、功能表、CI 表都很完整；ARCHITECTURE.md 与 AGENTS.md 也具备工程约束价值。
- 但存在明显滞后：
  - README 声称 957 个 GoogleTest、ctest 共 958 项；实际为 955 项。
  - `DOCS/KNOWN_ISSUES.md` 被 README 与 CMake 注释多处引用，但文件不存在。
  - `docs/compliance_baseline.md` 不存在，`docs/roadmap.md` 不存在。
  - MiBand “内核已启动”、WirelessIDS ✅、Camera ✅、GUIX ✅ 等表述缺少对应的真机/固件证据。
- `DOCS/` 目录本身只有少量架构、移植、安全说明，与 README 的详细程度不匹配。

## 六、README 目标达成度

## 七、主要风险与缺口

### P0：进入生产前必须解决

1. **没有真实硬件在环验证。** 4 个 QEMU 目标 + host 测试构成全部自动化验证；MiBand 8 与 Nucleo-L031K6 只有编译门禁，仓库内没有启动日志、烧录流程或 HIL 记录。
2. **生产安全配置未落地。** 除 nucleo 外的 5 个板级配置带 `CONFIG_OTA_DEV_MODE=1`（mock Ed25519），4 个 QEMU 目标与 nucleo 带 `DEBUG_BYPASS_SOFTBUS_KEY`；miband 虽有真实 OTP 密钥路径，但仍处于 OTA 开发模式。
3. **用户态/服务隔离不是默认执行模型。** 内置应用以 Kernel 特权任务运行；只有 ELF 加载路径使用 User；services 不是独立地址空间进程。能力模型在“代码层”成立，在“运行时隔离层”尚未完全成立。

### P1：显著影响完成度

4. **板级功能碎片化。** 扫描器/无线绑定仅 lm3s；virtio-net 未接防火墙/抓包；BLE 仅 miband；Lua/QuickJS 默认仅 miband；sensor/power/display 服务未进固件。
5. **真实驱动未标定。** ST7789、GT316、BHI260AP、DS3231、BLE UART 均缺真机时序/功耗/稳定性数据；BHY2 固件上传、DS3231 硬件闹钟未完成。
6. **质量门禁存在观察期。** 覆盖率阈值 0.0、32 位测试非阻塞、2 块板告警仅报告、2 块板无大小预算、合规检查可跳过。
7. **文档与代码漂移。** 测试数量、缺失文档引用、部分功能 ✅ 状态超前。

### P2：长期维护债务

8. `experimental/` 中 camera、NFC、GUIX、WiFi 与稳定代码边界清楚，但仍占用 README 的功能叙事。
9. AArch64 目标仍是 bootstrap 观察期；其 MMU 与中断路径的成熟度低于 ARMv7-M。
10. AI 子系统两套意图实现并存（legacy `intent_engine.hpp` 与 February），后续需要收敛。

## 九、如果恢复开发：建议优先级

1. **真机 bring-up 与 HIL**
   - 先做 MiBand 8 与 Nucleo-L031K6 的可重复烧录、串口日志、复位/看门狗测试。
   - 把现有 QEMU 串口断言扩展为真机 HIL 断言；至少覆盖启动、调度、VFS、显示、BLE。
2. **生产安全基线**
   - 移除所有板级的 `CONFIG_OTA_DEV_MODE=1` 默认值，改为显式开发构建开关。
   - 为 MiBand 增加生产 bootloader/密钥供应路径；关闭 `DEBUG_BYPASS_SOFTBUS_KEY`。
   - 建立威胁模型与最小攻击面清单，优先验证 syscall 边界、IPC 能力、OTA 验签。
3. **用户态与服务隔离**
   - 把内置应用逐步迁到 User 特权 + 能力化系统调用；把 sensor/power/display/vfs 服务变成真正独立任务/地址空间。
   - 删除或严格限制 `kernel/core/symbol_export.cpp` 的内核符号直出路径。
4. **板级功能矩阵收敛**
   - 明确每块板“支持/不支持”的功能清单，避免 README 用统一 ✅ 描述碎片化能力。
   - 把扫描器、PacketCapture、Firewall 在 virtio-net 上接通，形成完整数据路径。
5. **驱动标定**
   - ST7789/GT316/BHI260AP/DS3231/BLE 逐项做真机时序、功耗、长时间稳定性测试。
   - 完成 BHY2 固件上传与 DS3231 硬件闹钟，或明确降级为非目标。
6. **质量门禁收口**
   - 覆盖率阈值从 0.0 提升到基线值并设为阻塞。
   - 32 位测试转阻塞；补齐 rv32/aarch64 大小预算与告警基线。
   - 恢复 `compliance_baseline.md`，或删除该 job 的“阻塞门禁”表述。
7. **文档同步**
   - 修正测试数量、删除/恢复失效引用，给每个 ✅ 标注验证级别（host/QEMU/真机）。

## 十一、最终判断

AuroraOS 在约 4 个半月、931 次提交内，完成了从内核骨架到“QEMU 可运行 + 955 项测试 + 28 个 CI job”的工程闭环，这在同类个人/研究型 OS 项目中属于较高完成度。

它的主要成就是：

- 微内核主干真实存在，不是文档虚构；
- 能力、IPC、调度、内存、VFS、网络、UI、AI 都有可执行代码与测试；
- 测试与 CI 的工程化程度明显高于一般原型项目；
- 架构边界（内核不依赖 UI/应用/experimental）有可执行的门禁。

它的主要未完成项也同样明确：

- **没有真机在环验证**；
- **生产安全配置未启用**；
- **用户态与服务隔离尚未成为默认运行模型**；
- **板级功能碎片化、驱动未标定**；
- **文档与实现存在可核查的漂移**。

因此，将其定位为 **“Alpha 后期的微内核 OS 工程原型”** 是准确的；若以“可交付产品”为标准，完成度应按 30% 左右看待；若以“QEMU 可运行的研究/教学平台”为标准，完成度可视为 75%–80%。
